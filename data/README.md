# Cantarella group NetCDF provenance and validation

The source is `stick-number-bounds.nc`, [doi:10.7910/DVN/NFJIII](https://doi.org/10.7910/DVN/NFJIII). DataCite lists the dataset licence as Creative Commons Zero 1.0.[1] The unchanged 140,372,377-byte file is provided separately and linked under `data/external/crss/`; that directory is ignored by Git. The reader also accepts an explicit `EQUISTICK_CRSS` path. The source file is not part of this repository.

- SHA256: `a7e8bfc961bc2156d373ea206fc52beb3fbb122931f0743a979e5823de07cb22`.
- NetCDF4 groups: **12,965**, one named knot entry per group, with names `3_1` through `K13n...`.
- NetCDF global attributes: none.
- `sticks` and `crossings`: scalar `int64` variables in this file, not group attributes. The reader also accepts a one-element group attribute for a compatible export.
- `coords`: `float64` array of shape `(sticks, 3)`. Scale is not uniform: mean raw edge length is 1 for `3_1` and `9_29`, about 1.5818 for `K13n586`, and about 1.7590 for `K13n593`. Normalise before optimisation.
- `pdcode`: `int64` array of shape `(diagram_crossings, 4)`, with labels `0` through `2 * diagram_crossings - 1`, each used twice. Each four-entry row is passed unchanged to `spherogram.Link(pd)`, whose PD convention takes the incoming under-strand first and lists half-edges counterclockwise. On the sampled hyperbolic knots, the stored diagram and independently projected coordinates agree on knot type up to mirror image. This establishes operational compatibility with spherogram, **not** an independent geometric proof of the stored row ordering, crossing orientation or chirality.
- **Important distinction:** `crossings` counts crossings in the supplied projection, not the knot's minimal table crossing number. It equals the number of `pdcode` rows. It differs from the crossing number encoded in the group name for 12,962 entries. `crss_index()` and the census derive the latter from the group name and retain the source value as diagram metadata.

The reader opens the NetCDF4/HDF5 file lazily with `h5py`; eager `netCDF4.Dataset` materialises all groups and used about 3 GiB on this file. It rejects missing or ambiguous input paths, masked/fill values, non-finite coordinates, zero-length edges, malformed PD labels, and inconsistent array shapes for this source. **It is not hardened for arbitrary NetCDF metadata:** `_FillValue` and `missing_value` attributes are compared before their shape is bounded, which can create an enormous broadcast; `_scalar` reads a scalar variable before validating its dtype or payload size, and reads an attribute fallback before validating its shape. An independent security review failed on these two memory-safety findings. Do not point `EQUISTICK_CRSS` at untrusted files. The next session should add safe failing metadata-proxy tests, validate scalar dtype and size before reading, require scalar bounded fill sentinels before comparing, rerun the audit and census, and seek a new independent review. `data/crss_index.csv` lists each group, table crossing number, source sticks and raw `input_min_dist`. It contains **12,965** distinct rows. The complete geometry audit found finite coordinates and strictly positive `min_dist` for every group.

Stick-count frequencies for every crossing number from 3 through 13 match Table 1 of the Cantarella group paper exactly.[2] The identity audit used a deterministic 300-knot crossing-stratified sample plus all 19 known ten-stick cases, `9_29`, and eight torus knots, for **321 unique entries**. Of those, **319 matched** the stored names by numerical complement identification or torus checks. Two did not: `10_162` identified as `10_163`, and `10_86` as `10_83`, in both the stored PD code and the coordinate polygon. Their original names and source data were not changed. See `data/crss_validation.json` and `results/sweep/input_mismatches.csv`. The other 12,644 group identities were **not independently checked**; their census stick counts are provisional source metadata, not validated named-knot bounds.

`data/exact_stick_coverage.json` records separate saved-file verification for the 59 nontrivial knots in Eddy's exact-stick table: 23 have polygons in this repository, and 36 use hashed, read-only files in the external Eddy clone. Each has an outward interval certificate for the stored decimal geometric inequality and numerical knot-type checks. Eddy's coordinates are not copied into this repository. Numerical identification is not a formal knot-type certificate.

The derived `results/gap_census.csv` retains all 12,965 names. Its `input_status` is `matched`, `unchecked` or `mismatch`. For the two mismatched labels, `s_ub` and `e_ub_minus_s_ub` are blank; `source_sticks` retains the original count for audit. For unchecked rows, any `s_ub` and difference are **provisional** until that polygon is re-identified. The legacy `e_ub` field is a reported candidate count: `e_status=checked` for 20 selected in-repository files with numerical type and interval geometric checks, `reported_only` for 1,919 Eddy-only selections not checked in this census, and `none` for 11,026 rows with no such file. The separate exact-stick coverage report checks 36 Eddy files but the census conservatively leaves Eddy-only entries `reported_only`. An empty `e_ub` means no candidate file in these two sources, not non-existence. Positive `e_ub_minus_s_ub` is not evidence that `e(K) > s(K)`.

## Reproduction

Install `requirements.txt` and point `EQUISTICK_DATA` at the external Eddy clone. From `scripts/` with `PYTHONPATH=..`, run `crss_validate.py`, `06_verify_results.py`, `08_interval_certificates.py --expected-count 28`, `crss_verify_exact.py`, then `09_gap_census.py --expected-count 12965`. `crss_validate.py` currently writes its full report and exits 1 because the two input names disagree with both identity checks; that is a recorded finding, not an interrupted geometry audit. The validation and coverage JSON files record source hashes, package versions, code hashes, seeds, counts and individual outcomes. The raw NetCDF and Eddy coordinate files stay outside Git.
